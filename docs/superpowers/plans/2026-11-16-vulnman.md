# VulnMan (vulnerability management) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the SSD fall 2026 exam system: a vulnerability management app (intake → triage → assignment/SLA → remediation) with OIDC login, 4 staff roles plus a public reporting form, encrypted finding details, a tamper-evident audit trail, a dashboard and signed reports. It **replaces the quote app**: `cerberoast.site` becomes VulnMan, and quote-api/quote-web are retired (Task 22).

**Architecture:** Two apps, following the existing quote app's conventions:
- **`vuln-api`:** Go, stdlib `net/http`. It is also the OIDC client (backend-for-frontend), so tokens never reach the browser. It stores data in a per-environment Postgres.
- **`vuln-web`:** a React/Vite SPA served by nginx, on the **same origin**. Traefik routes `/api/*` and `/auth/*` to vuln-api, so there's no CORS and the session cookie works.

Identity comes from a **new, separate, public-facing Keycloak** (`keycloak-public`, `auth.cerberoast.site`). The existing Keycloak stays VPN-only for admin tools. Cryptography uses **Vault Transit**: per-finding envelope encryption, and Ed25519 report signatures. The app reaches Vault through the Kubernetes auth method already in place. Deployment uses the generic chart, ESO and ArgoCD, as quote-* does.

**Tech Stack:** Go 1.27 (`github.com/jackc/pgx/v5`, `github.com/coreos/go-oidc/v3`, `golang.org/x/oauth2`, nothing else without a reason), Postgres 16, React 19 + Vite + `react-router` 7 (only new frontend dependency), Keycloak 26 (keycloakx chart 7.4.0), Vault Transit, Helm, ArgoCD, Kyverno, cert-manager.

**Spec:** `docs/superpowers/specs/2026-11-16-vulnman-exam-spec.md` (vendored copy of the exam spec and hand-in requirements, upstream commit `519d59a`).

## Design decisions (the user skipped design questions; these are the planner's calls)

| # | Decision | Why |
|---|---|---|
| D1 | App names `vuln-api`, `vuln-web`. VulnMan **replaces quote-api/quote-web** (user decision 2026-11-16). Prod: `cerberoast.site` + `www.cerberoast.site` in the existing `cerberoast` namespace; `api.cerberoast.site` is dropped (same-origin `/api`). Dev/staging: `vulns-dev.admin.cerberus.internal` / `vulns-staging.admin.cerberus.internal` (VPN only, **no** oauth2-proxy gate since the app has its own login), replacing quote's admin-preview, in namespaces `dev`/`staging`. | Reuses the existing domain, certificate flow and namespaces. |
| D2 | BFF auth: vuln-api does the Authorization Code + PKCE (S256) flow as a confidential client, then issues a server-side session. Cookie `__Host-vm_session`, `HttpOnly; Secure; SameSite=Lax; Path=/`, absolute TTL 8h, idle TTL 30m. Only the **SHA-256 of the session ID** is stored in the DB. | Tokens never in JS (XSS can't steal them); a DB leak doesn't leak live sessions. |
| D3 | Separate Keycloak `keycloak-public`, realms `vulnman-dev`, `vulnman-staging`, `vulnman`. Public route exposes **only** `/realms/vulnman*` and `/resources/*`; the admin console is never routed (use `kubectl port-forward`). | The admin Keycloak guards Vault/ArgoCD; exposing it publicly would widen that attack surface. |
| D4 | One app role per user, from Keycloak realm roles `analyst`, `developer`, `pm`, `auditor` (claim `realm_access.roles`). A user with none of them is refused at login (403 page). More than one: the highest wins, `pm > analyst > developer > auditor`. | Spec roles map 1:1. |
| D5 | **Developer** sees all findings but may only edit/status-change findings **assigned to them**, and only to `In Progress` / `Remediated`. **Accepted Risk** may only be set by Analyst/PM. | Least privilege; the spec says "update status and details" without scope. |
| D6 | Status machine: `New→Triaged`, `Triaged→In Progress`, `In Progress→Remediated`, `Remediated→In Progress` (reopen), any non-final `→Accepted Risk`, `Accepted Risk→Triaged` (revoke). Everything else is rejected with 409. | Spec lists the states, not the transitions. |
| D7 | Severity: required enum `Critical/High/Medium/Low`, plus optional CVSS (0.0–10.0, one decimal) and optional CVE id (`^CVE-\d{4}-\d{4,}$`). | Spec allows "e.g. ... or CVSS". |
| D8 | SLA: PM-set days per severity, defaults **Critical 7, High 30, Medium 90, Low 180**. On `→Triaged` the due date = triage time + SLA, unless an Analyst/PM set an explicit due date. Overdue = open (not Remediated/Accepted Risk) and `due_date < now`. | FIND-04, FR-RPT-04. |
| D9 | FIND-11 encryption: `description`, `reporter_email` and attachment bytes are AES-256-GCM encrypted with a **per-finding data key** from Vault Transit `datakey/plaintext`. Only the wrapped key is stored. AAD = `"<finding id>:<field>"`, so ciphertexts can't be swapped between rows/fields. `title`, `asset`, severity and status stay plaintext so FIND-05 search works (documented trade-off). Transit keys are per environment: `vulnman-<env>-data` (aes256-gcm96), `vulnman-<env>-report` (ed25519). | The key never leaves Vault; it can be rotated with `rewrap`. |
| D10 | Audit (AUDIT-01..03): one `audit_log` row per mutation, written **in the same transaction**. Each row's `hash = SHA-256(prev_hash ‖ canonical JSON of the row)`, giving a hash chain. The app DB role gets only `SELECT, INSERT` on `audit_log`, and a trigger rejects UPDATE/DELETE. `GET /api/audit/verify` recomputes the chain. Details never contain decrypted plaintext. | Tamper-evident (stretch AUDIT-03) cheaply. |
| D11 | Two DB roles: `vulnman_owner` runs migrations (`vuln-api migrate`, as an initContainer); `vulnman_app` is what the server uses. The postgres superuser password exists only in the DB pod. | The running app can't alter the schema or audit grants. |
| D12 | Public report form (AUTH-03, FIND-02): `POST /api/public/reports`, no auth. Limits: 5 per IP per hour (in-memory; client IP only from `X-Forwarded-For` when the peer is in `TRUSTED_PROXY_CIDRS`), a honeypot field `website` (must be empty, otherwise silently accepted but dropped), body ≤ 32 KiB. The acknowledgement shows a reference `VM-XXXXXXXXXX` (10 random Crockford base32 chars). There's no e-mail sending (no SMTP in the platform); the contact e-mail is stored encrypted. | |
| D13 | Attachments (FIND-03): ≤ 10 MiB each, ≤ 20 per finding. Allowed types: `image/png`, `image/jpeg`, `application/pdf`, `text/plain`, `application/json`, decided by `http.DetectContentType`, **not** the client's header. Stored encrypted in Postgres `bytea`. Served with `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, and the stored type. | No extra object store to secure. |
| D14 | Scanner intake (FIND-09): Analyst/PM upload a Trivy JSON report (`trivy image --format json` **or** `trivy sbom --format json`, same schema). One finding per `(ArtifactName, VulnerabilityID, PkgName)`, deduplicated by a `fingerprint` against non-final findings. Trivy severity `UNKNOWN` → `Low`. Max 5 MiB / 2000 findings. | Covers the "Vulnerability scanning (Trivy etc)" intake channel. |
| D15 | Reports (FR-RPT-02/03): `GET /api/reports?from&to&asset` returns JSON `{reportJson, signature, keyVersion}` (the report as an exact JSON string, so verification is byte-exact), signed by Transit `vulnman-<env>-report` (Ed25519). The public key is at `GET /api/reports/public-key`; `cmd/vuln-verify-report` verifies offline. No PDF. | The spec allows "PDF or JSON"; the signature is the STRETCH. |
| D16 | PM role management (AUTH-04): vuln-api uses a separate Keycloak client `vuln-api-admin` (client credentials, realm-management `view-users` + `manage-users` in **its own realm only**). The API code only ever adds/removes the 4 app roles. A change deletes that user's sessions (effective immediately). | |
| D17 | MFA (AUTH-05, stretch): realm OTP policy (TOTP, SHA1, 6 digits, 30s), with `CONFIGURE_TOTP` as a default required action in the `vulnman` (prod) realm only. | Delegated to the IdP, as the spec asks. |
| D18 | Out of scope: "maybe disclosure" workflow (no role may approve disclosures in the spec), FIND-10 PM-tool sync (optional last task), PDF reports, e-mail. | |

## Global Constraints

- Every rule in `apps/README.md` "Image rules" applies: central base final stage (`ghcr.io/raiseofeasv/base-go`; web: `nginxinc/nginx-unprivileged:1.30-alpine`), numeric non-root USER, read-only root FS, listens on **8080**, answers **`GET /healthz`**, no CRITICAL with a fix, no env-specific values baked in.
- Each app has a `Justfile` with `build`, `test`, `lint`; `just test-all` / `lint-all` must pass in `pr-validate.yml` (GitHub-hosted runners, Docker available).
- Kyverno: resource requests+limits for cpu and memory, no `latest` tag, non-root, read-only rootfs, signed images.
- No secret value in git, Terraform state, Helm values or logs. Secrets live in Vault KV under `secret/vulnman/<env>/…` and reach pods only via ESO.
- Every `master` change goes through a PR with signed commits. Every commit carries the two `Co-authored-by` trailers (Andrii Savchenko, Ionut Andrei Grosu) plus the Claude line.
- API errors are JSON `{"error":"<message>"}` with the right status: 400 validation, 401 no session, 403 role/ownership, 404 not found **or not visible**, 409 illegal transition/conflict, 413 too large, 429 rate limited. Never a stack trace.
- All timestamps are stored UTC (`timestamptz`) and rendered in the browser's locale.
- Spec status strings exactly: `New`, `Triaged`, `In Progress`, `Remediated`, `Accepted Risk`. Severities exactly: `Critical`, `High`, `Medium`, `Low`.

## Review Focus

1. **Developer editing a finding not assigned to them**, or setting `Accepted Risk` → must be 403, and the audit log must not gain a row. Test in Task 6 (matrix) and Task 10 (HTTP).
2. **Hostile public submissions**: 1 MB body, HTML/JS in title/description, 6th submission within the hour, a spoofed `X-Forwarded-For` from an untrusted peer → 413 / stored verbatim and rendered as text / 429 / limited by the real peer IP. Tests in Task 11; the rendering test in Task 17.
3. **Ciphertext swap or tampering in the DB** (moving `description_ct` from finding A to B, flipping a byte) → reading fails with an error and returns 500 without leaking data, never someone else's plaintext. Tests in Task 7 and Task 8.
4. **Concurrent audit writes** (two mutations at once) → the chain stays linear and `verify` passes. A manual `UPDATE audit_log` by the app role fails. Tests in Task 8.
5. **Role revoked in Keycloak while a session is live**: a PM role change must invalidate sessions, and an expired idle session must return 401 (not stale data). Tests in Task 9 and Task 15.
